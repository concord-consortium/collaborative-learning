# Unit summary consumers

Four AI features read a unit's `aiUnitSummary` (see `docs/unit-configuration.md`): AdaChat, the AI Tile, Ideas, and Teacher Summary. All four go through the same two shared functions — `shared/unit-summary-slice.ts`'s `unitSummarySlice`/`formatUnitSummarySlice` — so the slice a consumer may send (current problem's cumulative `priorKnowledge`, that problem's own `problemDigest`, the next problem's `problemDigest`, and the current problem's `approach`/`approachGuidance`, checked against the unit's live problem list) is defined in exactly one place. What differs between consumers is *where* that call happens, *whose* current problem it uses, and how each one avoids serving stale context. This page records those differences; `docs/unit-configuration.md` covers the summary's own shape and the prefix check all four share.

## The two code-level instructions

Every consumer installs two instructions unconditionally — on every request, whether or not a slice applies, and whether or not the unit has an `aiUnitSummary` at all:

- **The no-look-ahead instruction** (`UNIT_SUMMARY_LOOKAHEAD_INSTRUCTION`): do not use curriculum content from more than one problem ahead of the student's current problem.
- **The problem-approach instruction** (`PROBLEM_APPROACH_INSTRUCTION`): follow the way the current problem asks students to work, and never suggest the opposite. It also covers a problem that changes approach between its parts, and says what to do when the model cannot tell which part a student is on — do not push either way.

Three of the four install them through one shared helper, `withCurriculumInstructions(systemPrompt, subject)` in `shared/unit-summary-slice.ts`, which prefixes both ahead of the authored `systemPrompt`. Keeping one helper is what stops the consumers from drifting apart. AdaChat is the exception: it installs them as separate conversation items rather than as a message prefix (see below).

**Teacher Summary gets different wording.** `subject` is `"the student"` for AdaChat, the AI Tile and Ideas, and `"the class"` for Teacher Summary, which selects `PROBLEM_APPROACH_INSTRUCTION_CLASS` instead. That version says "the class's current problem" and "the part the students' work shows they are on", because Teacher Summary describes a whole class's work to a teacher rather than talking to one student. The no-look-ahead instruction is the same for both subjects.

## The approach line in the slice

When the current problem has an `approach`, `formatUnitSummarySlice` adds one line after that problem's digest:

```
How this problem asks students to work (2.1): convergent. Students pick one design and improve it. Do not suggest starting over.
```

Three things about it:

- **Only the current problem's approach is sent, never the next problem's**, even though the next problem's digest is. A consumer that could see the next problem's approach might apply it early — pushing a student to converge in a divergent problem because the next one is convergent, which is exactly the contradiction this exists to prevent.
- **`unclear` sends nothing.** No line at all, rather than a line saying the problem is vague. The model then falls back to the standing instruction and whatever problem text it has.
- **The slice re-checks both fields before sending them.** `validateUnitSummary` runs when the authoring panel saves, but a `content.json` edited by hand in the curriculum repo never goes through it — and these fields reach the model as prose. So `unitSummarySlice` drops an unrecognised label (including a miscased `"Convergent"`), a guidance that is not text, or one over its length cap. Dropping costs only the approach line; the rest of the slice is sent as usual.

## AdaChat (the AI chat tutor)

The slice is built **client-side**, in `src/components/chat-tutor/unit-context.ts`, from the loaded problem model, not from any document field: `currentProblemOrdinal(problem)` walks up from the `problem` model to its parent `investigation` model and reads their ordinals directly. This is the same problem the student is actually looking at, on whatever branch they are actually running. Both instructions are installed server-side, unconditionally, in `functions-v2/src/chat/context-assembly.ts`, so they are present on every turn regardless of whether a slice applies.

AdaChat installs them as **two separate first-turn conversation items**, immediately after the generic prompt and before the LEFT problem item — not folded into the generic text. That is deliberate: a unit's `promptReplace` can swap out the generic text entirely, and neither rule may be removable that way. `src/components/chat-tutor/debug-transport.ts` shows both verbatim in the `chatDebug` view, since both constants live in `shared/` and are bundled client-side.

**The instructions reach new conversations only.** They are installed once, on a conversation's first turn, so a conversation that already existed will never receive them. Forking every existing conversation to deliver a policy change would restart every student's chat, which they would notice; the same choice was made for the no-look-ahead instruction when it was introduced. A *slice* change still forks, as described next — but that is the slice's content, not the instructions.

A conversation's Firestore document id (`conversationDocId`, in `src/components/chat-tutor/conversation-key.ts`) forks on a problem change (the problem path is one of its components) and on a hash of the *formatted slice text* (`unitKey`, in `chat-sidebar.tsx`), which forks the conversation when the slice's content changes **for the same problem**: an author edits or regenerates the unit's summary, or a curriculum edit flips the prefix check's result (the slice disappears, or reappears) without the problem itself changing. Hashing the formatted text rather than the `aiUnitSummary` object is what catches the "slice disappears" case — an object-level hash would not change when the object is still present but no longer produces a slice. This forking is skipped for the ForeverLearning (FL) provider (`shared/chat-tutor-providers.ts`'s `providerInstallsProblem`), which never attaches `unitContext` in the first place — computing and hashing it for FL would fork conversations for a value FL never uses.

**FL gets the summary a different way, manually.** On the FL chat path, no CLUE code sends the summary or the instruction to FL. FL gets both through the curriculum authoring UI's "Export for Forever Learning" view, which includes the summary, each problem's approach line, and both instruction texts; whoever configures FL copies that export into FL's own setup by hand, outside this codebase. That means FL's coverage of both rules depends on someone re-running that export (and updating FL's side) whenever the summary changes — there is no automatic path today.

## AI Tile

The slice is built **client-side**, in `src/plugins/ai/ai-tile.tsx`, from the document's own `unit`/`investigation`/`problem` — again, whatever branch the student is actually running. Both instructions are installed server-side, unconditionally, in `functions-v2/src/get-ai-content.ts`'s system-message builder, which calls `withCurriculumInstructions(systemPrompt, "the student")`.

Staleness is handled by the tile's response cache: `get-ai-content.ts` invalidates a cached response when the document's own prompt text changes (which includes the unit-context slice, since it is part of `dynamicContentPrompt`), when a class summary the tile forwards is regenerated (`summaryCreatedAt` changes — see Teacher Summary below), or when `PROMPT_POLICY_VERSION` bumps because the prompt-building code itself changed — it went to `2` when the problem-approach instruction was added, so every response cached under the older system message is regenerated. One known, pre-existing gap: the cache key does not include the unit's authored `systemPrompt` text itself, so an author editing that value alone does not invalidate an already-cached response.

The AI Tile is also where Teacher Summary's output reaches a student, indirectly: `get-ai-content.ts` forwards the class's `studentSummary`/`teacherSummary` (from the class data doc — see Teacher Summary below) into the tile's prompt. Those strings are already bounded by whatever slice Teacher Summary generated them with, so no separate filtering happens at this hop — see the class-level exception below for what that bound actually is.

## Ideas (the `aiEvaluation` / categorization pipeline)

The slice is built **server-side**, in `functions-v2/lib/src/ai-categorize-document.ts`'s `categorizeRepresentations`, from the document's own `unit`/`investigation`/`problem` as read from its Firestore metadata (`readDocumentMetadata`), falling back to the evaluation request's own context for a personal document, which has no curriculum fields of its own. Both instructions are installed unconditionally in `shared/ai-analysis-messages.ts`, via `withCurriculumInstructions(aiPrompt.systemPrompt, "the student")` in all three message shapes (image-only, summary-only, mixed) this consumer can send. Ideas' feedback to students — its `discussionPrompt` output — is covered by this, the same as its categorization.

Because this runs server-side with no browser session, it has no branch information for the class — see "the branch limitation" below.

**The AI harness does not send this slice.** `scripts/ai-harness/` builds its Ideas-shaped requests through the same shared message builders as production, so it now carries both instructions unconditionally too (its pinned request-key fixtures moved when each was added, for exactly this reason). It does not pass a `unitContext`, though: it has no fetched unit summary and no current-problem input to build one from. For a unit with an authored `aiUnitSummary`, harness prompts therefore differ from production's by this one slice. That is fine for the harness's present use; if it is ever used to evaluate the summary's own effect on Ideas' output, it will need a way to supply a unit summary and a current problem and pass the formatted slice through like every other consumer does.

## Teacher Summary (part of the "Class Summary" panel)

The slice is built **server-side**, in `functions-v2/src/on-class-data-doc-written.ts`, using the same `getUnitSummary`/`unitSummarySlice`/`formatUnitSummarySlice` functions the other consumers use. Both instructions are installed unconditionally, the same way, in this file's own system-message builder, which calls `withCurriculumInstructions(systemPrompt, "the class")` at both of its call sites (the per-chunk summarize call and the combine call). It uses LangChain's message classes rather than the raw OpenAI SDK shape the others build for, but the instruction text comes from the same helper.

**This is the one consumer that gets the class wording** (`PROBLEM_APPROACH_INSTRUCTION_CLASS`). Teacher Summary does not talk to a student — it describes a class's work to a teacher — so "the student's current problem" would not fit. It still needs the rule, because its `studentSummary`/`teacherSummary` text is forwarded into the AI Tile's prompt, where it reaches a student: a class summary that described the work in a way that pushed the opposite approach would carry that through.

**The class-level exception.** Every other consumer's slice is keyed on one student's own current problem. Teacher Summary's is keyed on the *class's* current problem instead: the furthest-along problem, in authored order, that any student in the class has done real work on — requiring both `documentHasStudentWork(content)` and `documentHasStudentEdits({changeCount, lastEditedAt})`. The edit check trusts `changeCount` when it's present (`changeCount >= 1`) and falls back to a non-null `lastEditedAt` only for older records that predate `changeCount`. Untouched templates have neither marker, so their content cannot advance the class; `changeCount` counts saved edits before disconnect. `lastEditedAt` is the weaker of the two signals — an Ideas click writes it whether or not the student edited anything — so a `changeCount` of `0` is not overridden by it; the one accepted residual is a legacy record with no `changeCount` whose `lastEditedAt` came only from an Ideas click, which still qualifies. This is computed in `shared/update-class-data-docs.ts` and stored as `currentProblemOrdinal` on the class data doc. The accepted consequence: a student behind the rest of the class can see, through the class summary the AI Tile forwards, curriculum context from a problem ahead of where they personally are. This is a deliberate, class-level narrowing of the "one problem ahead of the student" rule for this one path, not an oversight.

**Regeneration is not triggered by a changed summary.** A class summary is regenerated when the class's student work changes (the nightly scheduled pass, or the on-demand `generateClassData_v2` call the "Sort Work" panel makes), never by an edited or regenerated `aiUnitSummary` alone. A newly authored summary reaches an existing class summary the next time that class's work changes, not immediately.

**The branch limitation** (shared with Ideas): `shared/get-unit-summary.ts` always fetches the unit's `main` branch `content.json`, since neither consumer runs with a browser session or a branch recorded on document metadata. For a branch-preview deploy whose curriculum differs from `main`, the prefix check cannot detect that mismatch — both the summary and the live problem list it is checked against come from the same `main` fetch, so the check only proves internal consistency with `main`, not that `main` is what the class actually loaded. Accepted for v1: production classes run on `main`; a branch preview is development/QA use.
