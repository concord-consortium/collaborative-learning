# Unit summary consumers

Four AI features read a unit's `aiUnitSummary` (see `docs/unit-configuration.md`): AdaChat, the AI Tile, Ideas, and Teacher Summary. All four go through the same two shared functions — `shared/unit-summary-slice.ts`'s `unitSummarySlice`/`formatUnitSummarySlice` — so the slice a consumer may send (current problem's cumulative `priorKnowledge`, that problem's own `problemDigest`, and the next problem's `problemDigest`, checked against the unit's live problem list) is defined in exactly one place. What differs between consumers is *where* that call happens, *whose* current problem it uses, and how each one avoids serving stale context. This page records those differences; `docs/unit-configuration.md` covers the summary's own shape and the prefix check all four share.

## AdaChat (the AI chat tutor)

The slice is built **client-side**, in `src/components/chat-tutor/unit-context.ts`, from the loaded problem model, not from any document field: `currentProblemOrdinal(problem)` walks up from the `problem` model to its parent `investigation` model and reads their ordinals directly. This is the same problem the student is actually looking at, on whatever branch they are actually running. The no-look-ahead instruction is installed server-side, unconditionally, in `functions-v2/src/chat/context-assembly.ts`, so it is present on every turn regardless of whether a slice applies.

A conversation's Firestore document id (`conversationDocId`, in `src/components/chat-tutor/conversation-key.ts`) already forked on a problem change before this story — the problem path was already one of its components. What this story adds is a hash of the *formatted slice text* (`unitKey`, in `chat-sidebar.tsx`), which forks the conversation when the slice's content changes **for the same problem**: an author edits or regenerates the unit's summary, or a curriculum edit flips the prefix check's result (the slice disappears, or reappears) without the problem itself changing. Hashing the formatted text rather than the `aiUnitSummary` object is what catches the "slice disappears" case — an object-level hash would not change when the object is still present but no longer produces a slice. This forking is skipped for the ForeverLearning (FL) provider (`shared/chat-tutor-providers.ts`'s `providerInstallsProblem`), which never attaches `unitContext` in the first place — computing and hashing it for FL would fork conversations for a value FL never uses.

**FL gets the summary a different way, manually.** On the FL chat path, no CLUE code sends the summary or the instruction to FL. FL gets both through the curriculum authoring UI's "Export for Forever Learning" view, which already includes the summary and the instruction text; whoever configures FL copies that export into FL's own setup by hand, outside this codebase. That means FL's coverage of the no-look-ahead rule depends on someone re-running that export (and updating FL's side) whenever the summary changes — there is no automatic path today.

## AI Tile

The slice is built **client-side**, in `src/plugins/ai/ai-tile.tsx`, from the document's own `unit`/`investigation`/`problem` — again, whatever branch the student is actually running. The instruction is installed server-side, unconditionally, in `functions-v2/src/get-ai-content.ts`'s system-message builder.

Staleness is handled by the tile's response cache: `get-ai-content.ts` invalidates a cached response when the document's own prompt text changes (which includes the unit-context slice, since it is part of `dynamicContentPrompt`), when a class summary the tile forwards is regenerated (`summaryCreatedAt` changes — see Teacher Summary below), or when `PROMPT_POLICY_VERSION` bumps because the prompt-building code itself changed. One known, pre-existing gap (not introduced by this story, not fixed by it): the cache key does not include the unit's authored `systemPrompt` text itself, so an author editing that value alone does not invalidate an already-cached response. See the CLUE-678 Jira comment for the proposed fix.

The AI Tile is also where Teacher Summary's output reaches a student, indirectly: `get-ai-content.ts` forwards the class's `studentSummary`/`teacherSummary` (from the class data doc — see Teacher Summary below) into the tile's prompt. Those strings are already bounded by whatever slice Teacher Summary generated them with, so no separate filtering happens at this hop — see the class-level exception below for what that bound actually is.

## Ideas (the `aiEvaluation` / categorization pipeline)

The slice is built **server-side**, in `functions-v2/lib/src/ai-categorize-document.ts`'s `categorizeRepresentations`, from the document's own `unit`/`investigation`/`problem` as read from its Firestore metadata (`readDocumentMetadata`), falling back to the evaluation request's own context for a personal document, which has no curriculum fields of its own. The instruction is installed unconditionally in `shared/ai-analysis-messages.ts`, shared by all three message shapes (image-only, summary-only, mixed) this consumer can send.

Because this runs server-side with no browser session, it has no branch information for the class — see "the branch limitation" below.

**The AI harness does not send this slice.** `scripts/ai-harness/` builds its Ideas-shaped requests through the same shared message builders as production, so it now carries the no-look-ahead instruction unconditionally too (its pinned request-key fixtures moved for exactly this reason). It does not pass a `unitContext`, though: it has no fetched unit summary and no current-problem input to build one from. For a unit with an authored `aiUnitSummary`, harness prompts therefore differ from production's by this one slice. That is fine for the harness's present use; if it is ever used to evaluate the summary's own effect on Ideas' output, it will need a way to supply a unit summary and a current problem and pass the formatted slice through like every other consumer does.

## Teacher Summary (part of the "Class Summary" panel)

The slice is built **server-side**, in `functions-v2/src/on-class-data-doc-written.ts`, using the same `getUnitSummary`/`unitSummarySlice`/`formatUnitSummarySlice` functions the other consumers use. The instruction is installed unconditionally, the same way, in this file's own system-message builder (a local equivalent of the others', since this file uses LangChain's message classes rather than the raw OpenAI SDK shape the others build for).

**The class-level exception.** Every other consumer's slice is keyed on one student's own current problem. Teacher Summary's is keyed on the *class's* current problem instead: the furthest-along problem, in authored order, that any student in the class has done real work on — judged by the retrieved document's content (`documentHasStudentWork`), not by `lastEditedAt`, which is written only on disconnect and can lag behind work a still-connected student has already saved. This is computed in `shared/update-class-data-docs.ts` and stored as `currentProblemOrdinal` on the class data doc. The accepted consequence: a student behind the rest of the class can see, through the class summary the AI Tile forwards, curriculum context from a problem ahead of where they personally are. This is a deliberate, class-level narrowing of the "one problem ahead of the student" rule for this one path, not an oversight — recorded as such in the CLUE-678 Jira comment.

**Regeneration is not triggered by a changed summary.** A class summary is regenerated when the class's student work changes (the nightly scheduled pass, or the on-demand `generateClassData_v2` call the "Sort Work" panel makes), never by an edited or regenerated `aiUnitSummary` alone. A newly authored summary reaches an existing class summary the next time that class's work changes, not immediately.

**The branch limitation** (shared with Ideas): `shared/get-unit-summary.ts` always fetches the unit's `main` branch `content.json`, since neither consumer runs with a browser session or a branch recorded on document metadata. For a branch-preview deploy whose curriculum differs from `main`, the prefix check cannot detect that mismatch — both the summary and the live problem list it is checked against come from the same `main` fetch, so the check only proves internal consistency with `main`, not that `main` is what the class actually loaded. Accepted for v1: production classes run on `main`; a branch preview is development/QA use.
