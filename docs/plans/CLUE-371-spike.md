# CLUE-371 Spike: AI feedback should include Markdown/Images

Status: investigation sketch (not a finished plan)
Story: [CLUE-371](https://concord-consortium.atlassian.net/browse/CLUE-371)
Related: CLUE-607 (AI evaluations can include Agreements) is a clone of this story and builds on the summary/agreement machinery noted below.

## Goal

MODS students shouldn't get worse AI feedback depending on whether they describe their design in text or draw it. Today the curriculum author picks one representation (text summary OR image screenshot) to send for analysis. The story asks us to (1) improve the Markdown representation — especially of the drawing ("sketch") tile, (2) design a mixed-mode evaluation that sends the most information possible, and (3) reduce payload size where we can to conserve tokens.

## How AI evaluation works today (code map)

The pipeline is a three-stage chain of Firebase functions, driven by a Firestore queue:

1. **Trigger** — The client writes `evaluation/{evaluator}` metadata (timestamp + the unit's `aiPrompt`) whenever a doc is edited/closed (`src/lib/firebase.ts` — `getEvaluationMetadataPath`, `setLastEditedNow`, `setLastEditedOnDisconnect`). `functions-v2/src/on-analyzable-doc-written.ts` watches that path and enqueues an `AnalysisQueueDocument` into the Firestore `pending` queue.
2. **Summarize or screenshot** — `functions-v2/src/on-analysis-document-pending.ts` picks a `summarizer` (see "Which representation gets sent" below):
   - `"text"` → runs `documentSummarizer(content, {})` from `shared/ai-summarizer/ai-summarizer.ts` and stores the Markdown as `docSummary`.
   - `"image"` → renders the whole document via the Shutterbug service and stores a screenshot URL as `docImageUrl`. Note the hardcoded render target: `https://collaborative-learning.concord.org/branch/shutterbug-support` with `unit=mods`, height 1500.
   Result goes to the `imaged` queue.
3. **Analyze** — `functions-v2/src/on-analysis-document-imaged.ts` calls OpenAI (`gpt-4o-mini`, structured output via zod) through `functions-v2/lib/src/ai-categorize-document.ts`:
   - text path → `categorizeSummary()` → `buildSummaryMessages()` (also pulls in embeddings-based "related summaries" + teacher agreements from Firestore)
   - image path → `categorizeUrl()` → `buildImageMessages()` (single user message: prompt text + `image_url` part, `detail: "auto"`)
   The parsed response becomes a document comment (category tag + "Your work shows: …" + discussion). Token usage (`promptTokens`, `completionTokens`) and the full response are recorded in the `done` queue.

### Which representation gets sent (correcting/confirming our understanding)

The authored options are slightly different from "Text vs. Image vs. Custom" as three peers:

- `aiEvaluation` (unit config) selects the **evaluation method**: `"categorize-design"` (legacy built-in MODS prompt), `"custom"` (author-supplied `aiPrompt`), or `"mock"`. (`src/models/stores/unit-configuration.ts`, `docs/unit-configuration.md`)
- The **text-vs-image choice is a sub-option**: `aiPrompt.summarizer` (`"text" | "image"`). In the authoring UI (`src/authoring/components/workspace/ai-settings.tsx`, "Format Of Content Sent To AI") it is only editable when the method is Custom; `categorize-design` is forced to `"image"`.
- Fallbacks in `on-analysis-document-pending.ts`: if no summarizer is specified, docs whose Firestore metadata says `unit === "cas"` get `"text"` (a temporary hack), everything else defaults to `"image"`.

So: yes, we send text OR image, never both; Custom is where the prompt is authored, and the representation choice currently lives inside Custom's `aiPrompt`.

## Decisions so far

- **Model is fixed at `gpt-4o-mini` for this work.** Making model choice configurable is a plausible future story but out of scope here; all experiments and cost math below target gpt-4o-mini.
- **Text+image always, for everyone — the `summarizer` choice is gone (project team decision).** Every analysis sends both representations; there is no per-curriculum limitation to one or the other. The stored `aiPrompt.summarizer` property is ignored going forward (but stays *declared* in the MST unit-configuration model — existing published unit JSON contains it, and removing it from the model would break snapshot parsing; clean it from configs opportunistically). Definite consequences: the Shutterbug render-target fix is **promoted from in-scope to prerequisite** — units that never used the image path (`cas`, and anything future) will now be screenshotted on every analysis, and the hardcoded `unit=mods` + stale branch would render them incorrectly; the built-in `categorize-design` prompt ("This is a picture of a student document…") must be reworded and the authored MODS/cas prompts reviewed; the authoring UI's "Format Of Content Sent To AI" select and its validation go away; a **failure policy** must be chosen — recommended: degrade gracefully (screenshot fails → proceed text-only, and vice versa) with the degradation recorded in the `done` record; and `firebase.test.ts`, the pending/imaged function tests, the cypress `ai_evaluation` spec, and `docs/unit-configuration.md` all encode either/or today and need updating. Two notes: `cas` silently flips from text-only to mixed (higher cost, different feedback, for the RAG-loop pilot unit — worth one confirming sentence with the team), and the per-analysis cost floor rises for everyone, which makes the harness's cheap variants (`detail: "low"`, minimal summaries) more valuable.
- **Mixed mode should skip empty representations when that's straightforward.** (Still stands under text+image-always: that decision removes the *author-facing* choice; skipping a representation that would carry no content is an internal optimization, not a limitation.) If a document has no meaningful visual content, don't send the image; if it has no meaningful text content, don't send the (non-boilerplate) summary. Detection is cheap on the text side (the summarizer already walks every tile, so "no tiles that need visual representation" and "no text content" are easy to compute during summarization — using the per-tile-type capability flag described in finding 2, not a hardcoded tile list). Skipping the screenshot skips the Shutterbug call too, which also saves latency and a failure mode.
- **Fixing the hardcoded Shutterbug render target (`branch/shutterbug-support`, `unit=mods`) is in scope.** The fixed 1500px height can clip very long documents but real documents are typically shorter, so it's a minor concern; see the screenshot-strategy note below for the related per-tile-screenshots idea.
- **The offline harness is a keeper, not throwaway spike code.** It should live in the repo (e.g., under `scripts/`) so it can be re-used for future prompt/representation experiments — including the eventual model-choice work and CLUE-607 — and reviewed like any other code. Build it accordingly: checked in, documented, runnable by anyone with an OpenAI key.
- **Production analysis data is accessible, and the corpus strategy follows from what it contains.** We have access to the production database. The `done` queue accumulates indefinitely (the nightly cleanup only purges QA roots), and each record holds the exact model input for the path that ran (`docSummary` or `docImageUrl`), the `aiPrompt`, token counts, and the full AI response — enough to baseline the current system's cost and quality directly, and even replay historical runs (spot-check that old Shutterbug image URLs still resolve). For mixed-mode experiments, though, the queue only holds the one representation that ran, and the underlying document may have been edited since — so the harness corpus is built by using `done` records to *select* documents and provide historical stats, then fetching each selected document's current content via its `documentPath` and regenerating both the summary and the screenshot from that identical content for all variants. Two handling rules: corpus data (student work) stays out of git even though the harness itself is checked in; and re-sending production student work to OpenAI from the harness needs an explicit OK from whoever owns our data agreements (see team question 1).
- **Mixed mode carries over the text-path extras (related summaries + teacher agreements).** The vector/agreement RAG loop — today text-path-only and gated to `cas` — becomes part of the unified pipeline rather than being left behind. This works out naturally: the loop keys off the Markdown summary and its embedding, and mixed mode produces that summary anyway (except in the rare no-text skip case), so adding the image part doesn't disturb it. The hybrid message builder should therefore grow out of `buildSummaryMessages()` (prompt + summary + related summaries) with the `image_url` part added, rather than out of `buildImageMessages()`. Two consequences to track: (a) related summaries add up to five prior summaries plus agreement counts to every prompt, so the harness (step 4) should measure quality and token cost with and without them — and note that the feature as deployed has the bug described in finding 6a, so "with extras" must be measured in both `extras-production-current` and `extras-fixed` variants; (b) this extends the quoting of other students' AI summaries into a student's prompt from `cas` to every AI-feedback unit — the cross-student data-flow flag raised under PII below now applies broadly and is worth an explicit sign-off from the team (see CLUE-607).
- **PII: neither path deliberately strips it, so mixed mode makes nothing worse.** Verified in code: the text summarizer sends whatever students typed (tile text, table/data-set values, drawing text objects) with no redaction; the screenshot renders only the document content itself via the unwrapped read-only iframe (`iframe.html?...&unwrapped&readOnly`), so no student-name chrome is added around it. The one flow that moves data *between* students is the text path's related-summaries feature, which quotes AI summaries of other students' documents into the prompt — worth keeping in mind for CLUE-607, but it's not an image-vs-text asymmetry. If a redaction requirement emerges later it would need to be solved for both representations.

### Note: one big screenshot vs. several per-tile screenshots

Ethan raised whether capturing 3–5 individual tile screenshots instead of one full-document screenshot would reduce clipping. Cost-wise, with gpt-4o-mini's image-token accounting (a flat base charge per image, plus a per-512px-tile charge at high/auto detail — 5,667 tokens per tile, ~2,833 base):

- At `detail: "low"` each image costs a flat ~2,833 tokens regardless of size, so N screenshots cost N× what one costs. 4 screenshots ≈ 4× the price.
- At `detail: "auto"`/high, cost is dominated by total rendered area, which is similar either way, but each extra image re-pays the base charge — roughly 1.5× for 4 images vs. 1 in a typical case.

So multiple screenshots are meaningfully more expensive at low detail and moderately more expensive at high detail. The likely real win of per-tile capture isn't clipping so much as *legibility*: a full-document screenshot gets downscaled hard before tokenization, while a tile-sized screenshot keeps small text/sketch detail readable. Worth one harness experiment (step 4), but cheaper fixes for clipping exist: measure the document height (the render page already computes it via the `updateHeight` message) and pass the actual height to Shutterbug instead of a fixed 1500. A middle path if mixed mode wins: screenshot only the tiles whose content text can't carry and let Markdown carry the rest. Note that the set of such tiles is larger than "drawing" — see finding 2 — and must be determined per tile type via the summarizer's handler contract (a "needs visual representation" capability flag), never hardcoded as a list of tile names: new visual tile types will keep appearing, and curriculum that uses AI feedback won't always be limited to today's tiles.

## Key findings relevant to this story

**1. The drawing tile is nearly invisible in the text summary.** The tile handler used in the deployed cloud-function path (`shared/ai-summarizer/tile-summarizers/handle-drawing-tile.ts`) emits exactly: `"This tile contains a drawing."` An enhanced handler exists (`shared/ai-summarizer/ai-summarizer-with-drawings.ts`) that renders the drawing's objects to inline SVG, but it depends on `ReactDOMServer` and the drawing plugin's React components, so it can't run in Firebase functions today — it's only used by the standalone doc editor (`src/components/doc-editor/doc-editor-app.tsx`). This is the single biggest gap for "examine the MD representation of the sketch tile."

**2. Several other tiles degrade to weak or noisy text — and the set of "tiles text can't carry" is much larger than drawing + graph.** `handle-image-tile.ts` says only "This tile contains a static image." Tiles with no handler at all fall through to `generate-tile-description.ts`, which emits a property-by-property dump ("properties, x is 5, y is 10, objects is an array of 3 items…") — noisy for a model and expensive in tokens. The current coverage, from the tile registry and `shared/ai-summarizer/tile-summarizers/`:

- **Real handlers:** Text, Table, Graph (the XY-plot tile only — the handler checks `type === "Graph"` and does *not* cover Geometry), Dataflow (graphviz serialization), Simulator, Question, Placeholder.
- **Stub handlers:** Drawing ("This tile contains a drawing."), Image ("static image, no additional information").
- **No handler → property dump:** Geometry, Diagram, BarGraph, DataCard, Numberline, Expression, Timeline, WaveRunner, AI tile (Numberline and Expression get small special-case additions in the fallback; the rest get nothing meaningful).

Geometry stands out: a core tile with no meaningful text representation at all. Design consequence: whether a tile "needs an image" must be a **per-tile-type capability declared alongside its summarizer handler** — with unhandled/unknown types defaulting to "needs visual representation" — so mixed-mode logic never assumes today's tile set is final. This is also a quiet argument for mixed-mode-by-default: the visual-only set is large and will grow.

**3. Mixed mode is structurally easy at the OpenAI-message layer.** `buildImageMessages()` and `buildSummaryMessages()` each build one user message from content parts; a hybrid is just one user message containing the prompt text, the Markdown summary, and the `image_url` part. The real work is upstream in `on-analysis-document-pending.ts` (run both branches, carry `docSummary` and `docImageUrl` in the queue doc) and in deciding what happens to the summarizer setting/authoring UI.

**4. Token accounting already exists for baselining.** Every completed analysis lands in the `done` queue with `promptTokens`, `completionTokens`, and `fullResponse`. We can mine that (and the `failedImaging`/`failedAnalyzing` queues) to baseline current quality and cost before changing anything.

**5. Obvious size levers.**
- Summarizer options: `minimal: true` drops boilerplate and row/column structure (used by `update-class-data-docs.ts` already); the default (used for evaluation) includes full explanatory preamble and complete data-set case tables, which can dominate the payload for data-heavy docs.
- Image: `detail` is `"auto"`; `"low"` is dramatically cheaper (flat ~2,833 tokens on gpt-4o-mini) and may suffice for categorization. Screenshot is the entire document at a fixed 1500px height — possibly clipped or mostly whitespace.
- SVG-in-Markdown for drawings could be verbose; a structured natural-language serialization of drawing objects (type, position, size, color, text labels, stamp names) may carry the same signal in far fewer tokens.

**6a. Production bug: related summaries are the student's own summary, repeated.** In `findRelatedSummaries()` (`functions-v2/lib/src/ai-categorize-document.ts`), the loop over vector-search results pushes the *current document's* `summary` argument instead of each related doc's `doc.data().summary`. So the "similar document" summaries injected into the `cas` text-path prompt have been up to five copies of the student's own summary — the agreement counts attached to them are from the genuinely-related docs, but the summary text is wrong. (Found in an external review of the harness plan; verified in code.) Fix in production as part of this story or CLUE-607; the harness reproduces the buggy behavior as a named baseline (`extras-production-current`) so before/after comparisons stay honest — see the harness plan. This also means the extras' measured value to date reflects the bug, not the feature as designed. **Impact checked against production (2026-08-11, via `functions-v2/check-related-summaries.ts` plus a 30-day log search): zero real-world effect.** The entire production `summaries` collection contains one document — a single demo-class (`democlass1`/cas) interaction, alone in its context, so the search (which excludes the document being analyzed) could never have returned anything. Recent logs show only empty `relatedSummaries` arrays. The fix needs no data repair, and the extras feature has effectively never run for real — its value is genuinely unmeasured, which raises the priority of the harness experiments for CLUE-607.

**6. Cleanup candidates discovered along the way.** Hardcoded `unit=mods` and the `branch/shutterbug-support` URL in the screenshot renderer (now confirmed in scope); the `cas` unit special case; `summarizer` living inside `aiPrompt` (it configures transport, not prompting).

## Architecture alignment (relationship to the AI-architecture spike)

A separate spike surveys all six AI integrations across our codebases and asks what a unified design would look like (`report-service/docs/ai-architecture-comparison.md`, on the `ai-architecture-comparison` branch). We reviewed it and verified its claims against the code. **Decision: CLUE-371 proceeds now, without merging into or waiting on that spike.** The comparison doc itself supplies the justification: under both candidate end-state shapes it sketches (§8), the CLUE document-analysis system ("system D" in its taxonomy) stays where it is — batch, event-driven Firebase functions sitting next to the data in Google Cloud. It explicitly rates D a poor fit for the AgentCore direction (§7). The genuinely open architecture questions (Conversations API exit, AgentCore identity/triggers, cross-cloud state) concern the interactive systems — the chat tutors and DAVAI — which this story doesn't touch.

The overlap that does exist mostly runs the other way: three of the comparison doc's six consolidation targets (§5) are things CLUE-371 will build or improve. To keep that value, this work adopts the following guardrails:

- **Keep the summarizer a standalone library.** All drawing-tile / image-tile / fallback improvements happen inside `shared/ai-summarizer/` with no new dependencies on CLUE runtime code (the React-dependent SVG handler is the cautionary example). The comparison doc identifies this layer as one of two mature "domain object → LLM text" products in the org worth treating as reusable in its own right.
- **Build the harness as the estate's eval harness in spirit.** Only DAVAI has an eval/regression harness today; ours will be the second. Keep the corpus format and the message-shape/experiment layers cleanly separated from CLUE-specific loading code so it can grow beyond this story.
- **Extend, don't fork, token accounting.** CLUE's `done`-queue `promptTokens`/`completionTokens` is the only spend tracking in the estate. Baselining and any new mixed-mode metrics build on it rather than inventing a parallel mechanism.
- **Preserve prompt-as-data.** The comparison doc calls CLUE's authored `aiPrompt` + derived response schema the strongest prompt-configuration pattern in the org. Any rework of where `summarizer` lives must not regress it.
- **Don't deepen OpenAI coupling.** The analysis path's plain chat-completions + zod calls are rated medium-portability; mixed mode (text + image parts in one message) doesn't require anything provider-proprietary, and we keep it that way. (Model stays `gpt-4o-mini` per the decision above — this guardrail is about API surface, not model choice.)

Rework risk if a unified architecture later changes D's substrate: low, and mostly self-insuring — the mixed-mode work lives in the summarizer and message-construction layers, which are exactly the layers any future architecture would reuse. What CLUE-371 feeds back to the architecture spike: a reusable eval harness, a strengthened shared summarizer, and measured token/quality data for text vs. image vs. mixed representations.

## Sketch of an investigation approach

1. **Assemble a test corpus + harness.** Per the production-data decision above: select documents and pull historical stats from the `done` queue, then fetch each selected document's current content and regenerate all representations from it. Build a small offline harness that can run any (summarizer × prompt × message-shape) combination against the corpus outside the deployed pipeline — `categorizeUrl`/`categorizeSummary` and `documentSummarizer` are all importable and already unit-tested, so this is mostly wiring. Per the decision above, the harness is checked into the repo (e.g., `scripts/`) as a reusable tool, so give it a real CLI, a README, and sensible corpus-file conventions. All runs stay on `gpt-4o-mini` per the decision above. Without this we can't say "better" with any confidence. **Detailed plan: [CLUE-371-harness-plan.md](./CLUE-371-harness-plan.md)** — buildable now; only the production-corpus pull and rubric scoring wait on the team's answers.
2. **Define "good feedback".** Even a lightweight rubric (does the category match a teacher's judgment? is the discussion specific to the student's actual design?) scored on ~20–50 docs. Ideally reuse teacher agreement data (`aiAgreements`) as ground truth where it exists.
3. **Improve the drawing-tile Markdown.** Two candidate paths to prototype and compare: (a) a React-free SVG serializer for drawing objects usable in functions; (b) a structured text description (objects, positions, labels, stamps, text elements). Measure both for quality lift and token cost. Same pass can fix the image tile (include URL/dimensions/caption), tame the generic property-dump fallback, and audit every registered tile type to classify its summarizer fidelity (full / partial / visual-only), recording that as the per-tile "needs visual representation" capability flag from finding 2. Geometry is the highest-priority gap after Drawing.
4. **Prototype mixed mode in the harness.** Text + image in a single user message, against text-only and image-only baselines, on the same corpus. Include the skip-empty-representation logic from the decision above, and run with/without the related-summaries + agreements extras (now carried over per the decision above) to measure their quality lift and token cost in the mixed setting. Also test cheap variants: image `detail: "low"`, `minimal: true` summaries, summary-without-dataset-tables, accurate-height screenshots, and one per-tile-screenshots run (or drawing-tiles-only screenshots) to see whether the legibility gain justifies the extra per-image cost.
5. **Implement the config decision (settled — see "Text+image always" in Decisions).** The team decided: text+image all the time, no per-curriculum limitation; `summarizer` is ignored (kept declared in the MST model for snapshot compatibility). Implementation items: delete the summarizer/default/`cas`-hack logic in `on-analysis-document-pending.ts`; remove the format select + validation from `ai-settings.tsx`; reword the built-in `categorize-design` prompt and review the authored MODS/cas prompts (all worded for a single representation today); implement the graceful-degradation failure policy; update `firebase.test.ts`, the pending/imaged function tests, the cypress `ai_evaluation` spec, and `docs/unit-configuration.md`. An earlier concern — auditing existing configs to distinguish deliberate `summarizer` values from authoring-form residue — is moot now that all values are ignored.
6. **Then write the real implementation plan** covering `on-analysis-document-pending.ts` (produce both artifacts; the render-target fix is a prerequisite), `on-analysis-document-imaged.ts` / `ai-categorize-document.ts` (hybrid messages), authoring UI, docs, and cost guardrails.

## Questions for the project team

One question remains open; step 2 (the rubric) depends on it. (Question 2, the config blessing, was answered: text+image always, no per-curriculum limitation — recorded in Decisions and step 5. One small residual from that answer: confirm the team's "no limitation" knowingly includes `cas`, the RAG-loop pilot that deliberately chose text-only.)

1. **Ground the fairness hypothesis and define quality.** Reframed from the earlier "what's poor about current feedback?": the story's premise is not that feedback is bad in general, but that single-representation modes are *unfair across work styles*. MODS is in image mode, so a student who draws is well served while a student who writes has their words reduced to pixels in a downscaled screenshot; text mode would flip and worsen the gap (drawings become "This tile contains a drawing"). The two blind spots are asymmetric — text mode erases drawings, image mode merely degrades writing — which is presumably why MODS chose image, and it predicts the specific failure to look for: evaluations that ignore or misread written content that was present but illegible. The questions for the team:
   - *Is the gap observed or expected?* Have teachers or the team actually seen evaluations that missed or misread a student's work — especially students who described their design in words? If yes, a handful of examples (document, what the evaluation said, what it should have said). If it's an expected risk rather than an observed problem, that's fine — it changes how we measure, not whether.
   - *What does a good MODS evaluation look like?* The feedback has three parts (category, "your work shows" list, discussion). What matters most — correct category, discussion that references the student's actual design specifics, something else? What makes an evaluation poor?
   - *Who can judge?* Can a teacher or curriculum person rate ~30–50 evaluations in a blinded side-by-side review (we build the review sheet; they don't see which configuration produced which feedback)?
   - *What's the mix of work styles?* Roughly what share of MODS students draw vs. describe vs. both? The test corpus needs enough of each kind to measure the gap.
   - *Data agreements:* an explicit OK from whoever owns them for pulling production student work to dev machines and re-sending it to OpenAI from the harness (same processing production already performs, but signed off rather than assumed; note the related-summaries data contains other students' information).

   Success criterion this implies: mixed mode is at least as good as today for students who draw, better for students who describe, at acceptable token cost — measured per work-style group, not as an overall average (an average could hide exactly the gap this story exists to close).
